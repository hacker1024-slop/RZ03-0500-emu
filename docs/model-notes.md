Flash captures are external inputs. A fully valid 16-byte capture word is treated as programmed; a byte-validity mask is not a measurement of physical ECC cells. For captures spanning the application, the explicitly supplied application image takes precedence. CPU reset preserves simulated nonvolatile data; it reloads the selected application handoff. Both image bytes and simulated erase/program effects remain private unless a caller explicitly exports them.

## EZH backend assessment

[ErichStyger's QEMU fork](https://github.com/ErichStyger/qemu), inspected at revision `6a14bf40bd46fea99dbf240340afb4acd69b924c`, contains an architecture-B target, disassembler and QMP register access. Its decoder currently lists eight instruction patterns. It lacks `E_PER_READ`, shift operations and heartbeat timing used in this firmware's startup, and its standalone MCXN947 board's peripheral reads/writes are placeholders. It is a useful reference and potential future backend, but does not yet replace a complete LPC5528 platform. The target files are LGPL-2.1-or-later; its machine implementation is GPL-2.0-or-later. No fork source has been copied into this repository.

The Renode peripheral interprets an initial instruction subset using its existing bus and virtual timers. It executes the original EZH mailbox setup, stack-pointer load, input-buffer pointer load and GPIO register initialization. Heartbeat/wait synchronization, basic arithmetic, fused pre-shift AND/OR/XOR/ADD/SUB, immediate/register branches, scheduled branches with two delay slots, absolute subroutine calls and tight loops are implemented. Synthetic tests cover synchronization, delayed PC writes, call/return behavior and loop prologue/exclusive-end semantics. Instruction timing and pipeline interactions are functional approximations.

`INT_TRIGGER` pulses a common interrupt output and each selected channel among 24 outputs. The LPC5528 board connects the common output to NVIC30, matching the original application's enable bit and handler at 0x20003C00. NXP's [LPC55S16 keyscan example](https://github.com/nxp-appcodehub/dm-lpc55s16-keyscan-by-ezh/tree/89f193831509240046106d80369bc800d2abf49c) independently uses Reserved46_IRQn (NVIC30) for EZH completion, without a SYSCON hijack setup. This corroborates a family-level routing inference rather than treating MCX channel-hijack registers as LPC registers. Additional channel outputs remain unwired. Tests use the board connection for common pending bits and synthetic connections for extra channels, including channel 23, an unselected channel and a zero channel mask. Writes to EZH2ARM pulse the common output only when ARM2EZH bits 1:0 equal 2. The interrupt operand overlaps the usual condition field and is decoded unconditionally. An optional private-image integration test executes the original Thumb ISR and verifies that it clears EX and sets the matrix-ready flag in RAM.

EZH bus exceptions stop execution with `ezh_bus_fault` and an independent address, preserving the faulting instruction PC. Tests cover both instruction fetch and data load faults without setting Cortex-M fault registers. Hardware emergency-vector execution and the control register's bus-error-ignore option remain unimplemented; this explicit stop is a model limitation.

The Boolean detector is a separate component implementing eight input selectors, all eight event modes, sticky-edge clearing on CFM writes, AND groups with OR-enabled outputs (AN14650 figure 8), and pending-trap capture/override. CFS reads report selected input levels in their read-only low byte. Pending-trap polarity selects rising versus falling edge capture; it does not invert software-written override status. The eight trigger inputs can receive Renode GPIO signals, but are not yet connected through LPC5528 INPUTMUX or board wiring.

Plain HOLD waits without completing instructions until the combiner fires. Vectored HOLD selects the lowest-numbered firing group, supports 4/16-byte vector stride, NRA, and selected-vector acceleration with two unflushed instructions. Pending scheduled branches are retained independently, including a branch issued in an accelerated HOLD delay slot. Tests check edge histories, sticky clearing, the cookbook's ABC+D+EFGH cascade, pending capture and polarity, wait/resume, competing vectors, acceleration and overlapping branches. The functional model saves the next instruction as RA for ordinary vector dispatch and the address after two delay slots for accelerated dispatch; these return-address details and exact dispatch latency have not been checked against silicon. Ignition restart discards the old execution pipeline; full peripheral reset additionally clears detector configuration and input state.

The ANACTRL FRO192M_CTRL/XO32M_CTRL defaults also follow the device pack. These are documented reset values, not measurements of the physical keyboard. USB register layout and endpoint command encoding are cross-checked against the [NXP USB middleware](https://github.com/nxp-mcuxpresso/mcuxsdk-middleware-usb) at `b330ba1e98bec0faa1b97fdf772bf81803a05868`; no middleware source is vendored.

With the private settings captures and no host attached, the Cortex-M33 runs for 500 ms (48,000,000 instructions) without reported CPU faults or unsupported accesses. The PHY reports functional readiness and the device controller is enabled, with endpoint list at 0x40100100. It remains in the initialization wait loop at 0x2000C468–0x2000C476, waiting for firmware USB state. This is not completed boot.

With external VBUS present, the model signals the HS attachment event documented in the NXP driver's ISR: DEV_INT, OTG_C and LPM.ADPPROBE. It also signals an already-present host when firmware enables the controller. The original firmware's IRQ47 handler processes this event and sets DCON itself. Private-image integration tests check both attached and detached startup. No controller or firmware patch sets DCON on behalf of firmware. The bit-27 change flag and ADPPROBE behavior are described by NXP's USB driver even though omitted from the public LPC5528 SVD fields.

The packet engine uses HS endpoint commands: 11 address-offset bits in units of 64 bytes, a 15-bit remaining count, and the ACTIVE/DISABLE/STALL flags. Buffers reside in the fixed USB RAM window. It tracks progress across packets, signals completion on an exhausted count or short OUT packet, advances double-buffer selection, and cancels both banks on endpoint abort. A new SETUP clears control STALL/active state and writes its eight bytes into the firmware-selected setup buffer. Bus reset changes protocol address/speed/status without resetting the CPU or RAM. Invalid DMA or unsupported transfer behavior stops as `unsupported_usb_transfer`, separately from CPU faults and unknown MMIO. Actual hardware error reporting for such invalid transfers is not modeled.

The reusable Python host advances virtual time while waiting for NAKs and exposes control requests, bounded timeouts and distinct STALL errors. It allows 10 ms of virtual reset recovery and 2 ms after assigning an address; these functional host delays do not constitute a cycle-accurate bus model. The CLI's `--usb-enumerate` performs address assignment and selects the first configuration.

Verified against the private 1.1.1 application and settings: the firmware returns its 18-byte device descriptor (1532:02A5), 134-byte configuration with five HID interfaces, product string, and HID report descriptors of lengths 61, 177, 88, 22 and 327. SET_CONFIGURATION succeeds and firmware leaves its initial USB wait loop. Tests also exercise short descriptor responses, an unsupported-descriptor STALL followed by recovery, and a 90-byte Razer SET_REPORT/GET_REPORT exchange: command 00/87 returns status 2, version 1.1.1 and a valid report checksum. These data are produced by the original firmware, not host-side descriptor or Razer-command tables. Interrupt input reports and USB key transitions remain unverified. Lighting register traffic is covered below.

The EZH has completed 43 instructions and waits at `0x200010AC`, a vectored-HOLD-shaped word (`0x2000161C`) in an apparent inline pointer table. CFM's reset routing produces no Boolean event, so it remains held with the currently unconnected inputs.

The intended pointer-table control flow remains unresolved. The preceding pointer-shaped word also decodes as an interrupt trigger; interpreting these words is not evidence that the intended scanning path is correct. No table entries or application instructions are patched. Breakpoint address/vector registers are both zero, so breakpoint redirection does not explain this path. Board routing, the remaining instruction set, USB hardware and physical EZH I/O wiring remain incomplete. This checkpoint is not a working matrix scanner or USB keyboard.

The decoded initialization sets eight EZH output bits (`7, 1, 17, 16, 23, 10, 15, 31`) and clears sixteen direction bits (`30, 29, 19, 6, 4, 3, 2, 25, 22, 21, 24, 28, 26, 18, 9, 27`). This is consistent with an 8×16 scan matrix; that is an inference, not a verified key-to-pin mapping. CPU scanner pin tables corroborate the port-zero mapping described below. Physical key positions and entry into the scanning loop through normal startup still need validation.

After host bus reset, the controller generates SOF interrupts on Renode's virtual clock. The functional model uses 125 µs microframes at high speed and 1 ms frames at full speed; INFO's 11-bit frame number advances every millisecond and wraps at 2048. High-speed FRAME_INT is generated per microframe. That interrupt granularity is an assumption based on USB microframe timing, not a measurement of this LPC5528. The clock stops on disconnect, controller disable or the modeled suspend flags, and MCU reset requires a new host bus reset. Analog frame synchronization and suspend/resume signaling remain unimplemented. Original-firmware enumeration and the version feature-report exchange continue to pass with this clock enabled.

With DMA request gating and abort controls modeled, the configured private firmware runs to about 158 ms without CPU faults or unsupported accesses. It attempts an I2C transaction to unconnected address 0x50, receives NACK and aborts DMA channel 13. No DMA success is fabricated for that address. Synthetic integration separately verifies successful I2C DMA writes against Renode GenericI2cEeprom. This test peripheral is not installed as a substitute for the keyboard's unidentified external controller. EZH remains at its existing HOLD checkpoint, so this is not working keyboard scanning.

DMA default request-channel assignments are cross-checked against NXP's [LPC5528 inputmux definitions](https://github.com/nxp-mcuxpresso/mcux-sdk/blob/main/devices/LPC5528/drivers/fsl_inputmux_connections.h); the public device pack resets DMA0_REQ_ENA to 0x7FFFFF. Inputmux request-enable writes and alternate hardware trigger routes are not accepted by the platform yet. Copying and descriptor completion are bounded to one beat per service tick, including self-referencing descriptor chains. DMA bus access exceptions set ERRINT without setting completion flags.

The immediate-shift family now includes the scanner's conditional shift-and-OR bit accumulation. The shift runs before the fused ALU operation; subtraction uses the shifted value as its left operand. Flag-setting ADD/SUB uses arithmetic carry, while logical forms preserve the shift carry. Conditional false instructions skip the whole operation. ADC/SBC fusion and SPO/SNE algorithmic conditions remain explicitly unsupported. This removes a later scanner-path limitation, but does not resolve startup control flow.

A private-image host-attached run to 558 ms still leaves EZH at 0x200010AC with 43 completed instructions. The NOP at 0x200010A0 and following pointer-shaped words match in the installed dump and extracted updater image. A bus write trace through the first 20 ms observes only the expected EZH control/mailbox/boot writes, with no CPU write replacing that NOP or programming breakpoint vectors. Startup relocation or another missing execution detail remains under investigation. These observations do not justify changing the NOP or skipping the following data-like words.

An extended byte/halfword/word write trace, with matrix attachment and USB enumeration, still finds no CPU write replacing the NOP through 343,360 µs. It observes normal EX updates through the existing control-register routine. This extends the earlier startup-only observation to include configured USB and later polling; it does not establish the missing instruction-fetch behavior.


## Application handoff and lighting evidence

The captured bootloader routine at 0x62FC copies the application from flash 0x8000 into RAM 0x20000000 using the length in the header at 0x7800, sets PSP/VTOR and branches to the application reset vector. A private probe executes this routine against an executable Renode ROM mapping and observes an exact application-image match at the branch target, including the NOP at 0x200010A0. This copy routine does not repair that instruction. The production ECC flash peripheral is CPU-readable MMIO, not an executable ROM mapping; direct flash execution stalled the private probe. The executable diagnostic mapping is not enabled in the core.

After the specimen's first-page ECC repair, a fresh three-read acquisition verifies all 32,768 bootloader bytes with no holes, SHA-256 `a34935e307515302d8c082c3c85a792d7109699d0105dbebdbfdd11577b63acd`. The initial SP is 0x04008000 and reset vector is 0x215. The capture restores normal keyboard mode successfully, and every previously readable bootloader byte matches the older capture. It supersedes the earlier incomplete bootloader capture; the earlier first-page hole was a specimen ECC fault, not a fixed read restriction.

Running this complete bootloader from its reset vector in the private ROM mapping exposes PMC.AOREG1 at offset 0x84. That always-on 32-bit storage now starts at zero on a new virtual board and retains its value across MCU reset, consistent with the public LPC5528 header's reset domains. The bootloader then reaches application handoff without unsupported accesses. At handoff, RAM exactly matches the selected application and all EZH registers remain zero. A separate uninterrupted run through reset and handoff reaches the same 43-instruction EZH HOLD by 30 ms and remains there at 80 ms, without CPU faults or unsupported accesses. Continuing that uninterrupted run enumerates the original five-interface USB device at 98,020 µs while EZH remains at the same HOLD. Thus the complete boot path does not resolve the scanner startup issue. This diagnostic mapping cannot reproduce ECC faults on direct CPU flash reads; it is evidence about this observed boot path, not a production cold-boot implementation or a replacement for the ECC model.

A subsequent read-only acquisition of application slot B (flash 0x26000–0x44000, end excluded) independently verifies its first 97,280 bytes against two marker reads and a third verification read. Those application bytes exactly match slot A, SHA-256 `85813c29d04bf853a1eef07fd3e5744c50c9e434e9c3f0c4feb0663b8f549ad1`, including the NOP and dispatch table. The remaining 25,600 bytes are unreadable and retain explicit validity-mask holes; they are not evidence of erased flash. Normal keyboard mode is restored successfully. A different application in slot B therefore does not explain the observed EZH startup path. The private capture is not distributed with the emulator.

Supplied teardown photographs directly identify the NXP MCU and a RAZER CHROMA 192 main-board lighting package. They also show a separate media board and another unidentified controller-board IC. No photograph establishes a connector pinout or an original manufacturer part number for the lighting package.

The original application attempts Flexcomm4 addresses 0x50/0x5F/0x53 and Flexcomm2 address 0x5C. A diagnostic register target at 0x50 allows capture of its intended writes: FE=C5 unlock, FD=03 function page, 00=01, 01=FF, 0F=07, 10=07, followed by page-1 PWM data (192 bytes) and page-0 enable data (24 bytes). This matches the [IS31FL3733 register layout](https://www.lumissil.com/assets/pdf/core/IS31FL3733_DS.pdf) and supports the compatible lighting model described below. It does not identify the exact branded silicon or populate guessed devices in the production platform. A generic register target is not a working LED driver model.

Earlier private experiments connecting the EZH common interrupt to NVIC30, driving the inferred column inputs plus P0_20/P1_0 high, and combining those changes all leave the same HOLD checkpoint after USB configuration and 200 ms of execution. Later NXP example evidence corroborates the common interrupt route; the extra input-level guesses are not installed in the board. A startup write trace covering byte, halfword and word accesses also finds no write replacing the NOP during the first 20 ms.

The earlier one-shot GPIO input experiment did not separate external signal levels from IOCON pull defaults. The GPIO adapter now records external receiver levels separately, so later weak-pull configuration cannot overwrite a driven input. External inputs remain driven across MCU reset, and `ReleaseInput()` returns a pin to its pull default. This is a functional digital distinction, not an electrical contention model. Corrected probes hold P0_20/P1_0 at all four combinations throughout startup; the firmware records modes 1, 3, 2 and 4 respectively, confirming that the inputs reach its mode-selection routine. All four runs still reach the same 43-instruction HOLD after enumeration and 100 ms of further execution. No guessed mode straps are installed by default.


## CHROMA 192-compatible lighting model

`Chroma192.cs` implements the observed register protocol using the [Lumissil IS31FL3733 Rev. G datasheet](https://www.lumissil.com/assets/pdf/core/IS31FL3733_DS.pdf) as the compatibility reference. It is attached only through an explicit bus/address selection; the production platform does not assume every probed address is populated. The model implements the FE=C5 one-write unlock for FD page selection, auto-incrementing transactions, 24 on/off bytes, 192 PWM bytes, global current, software shutdown and the page-3 reset-register read. Page-2 mode selection and inactive breathing configuration are stored; enabling breathing or electrical detection stops explicitly because their time/physical behavior is unimplemented. Read-only open/short status is zero for the model's healthy loads. Physical SDB and synchronization pins are not wired.

The frontend wrapper returns immutable snapshots in driver channel order. Logical levels multiply PWM and global current and apply the packed on/off mask; these values do not establish actual optical intensity or a key/RGB mapping. Unsupported operations remain sticky across an I2C reset-register read and are cleared by core reset. Configured attachments survive reset.

An original-image integration test polls for the firmware's enable-byte write, interleaved with its other I2C address probes, rather than assuming a fixed initialization time. A private run to 443 ms observes initialized enable bytes and changing PWM data from the original application. EZH remains at its existing HOLD checkpoint; successful lighting traffic does not establish a working keyboard scanner.

Lighting register reads also exposed an I2C DMA over-read: eagerly fetching the next byte after every DMA read fetched one beyond the requested transfer. Receive data is now consumed lazily per DMA beat. A single-byte FE read, whose successor FF is unsupported, verifies that no extra register read occurs.

Lighting initialization also exposed a DMA trigger-lifetime bug. NXP's LPC5528 header specifies that CTLSTAT.TRIG clears at the end of an entire transfer; CLRTRIG additionally clears it during descriptor reload. Keeping TRIG after an unchained completion allowed a subsequent CFGVALID write to start a transfer before a fresh SWTRIG, causing timing-sensitive I2C payload delivery. Completed unchained transfers now clear TRIG, and a regression test rearms a channel without triggering it, verifies no data movement, then issues SETTRIG and checks the transfer. The original-image lighting initialization passes without CPU watchpoints.


## Matrix contact model

`DiodeMatrix.cs` provides an ideal active-low matrix with pulled-up columns and per-contact diodes, connected to the EZH digital input register through a combinational input provider. Row/output direction changes take effect on the next input read. Only driven-low output rows close a pressed contact to an input column; high-impedance rows do not pull columns down. Driven output pins read back their output level, and non-matrix input pins default low. This models digital levels only, without switch bounce, analog contention or electrical timing.

Attachment is explicit through `Keyboard.attach_matrix()`. Its 8×16 pin-index layout follows the original EZH program's GPO/GPD initialization. The original application's CPU scanner tables independently list the same rows and columns as GPIO port-zero pins, in the same order. Pin indices are not package pin numbers. IOCON function 0 selects CPU GPIO and function 15 selects EZH as the driver of each pin; other alternate functions contribute no drive to this model. GPIO byte/word pin aliases, PIN, MPIN and SET reads observe the same physical contacts as EZH GPI. GPIO masks apply to MPIN reads only, and non-matrix input levels remain supplied by Renode GPIO. This is a functional digital mux, without analog behavior or a complete implementation of other alternate functions. Boolean trigger INPUTMUX and physical key positions remain unconnected. The separate encoder API drives GPIO1 pins 2/3. Attaching it does not resolve the normal startup HOLD. Held contacts belong to the board and survive an MCU reset.

Synthetic integration tests exercise released pull-ups, row selection, high-impedance rows, release, prevention of a three-contact ghost rectangle, and the scanner's BTST/conditional-shift-and-OR accumulation through GPI. A private component probe first observes normal startup at the existing HOLD, then explicitly selects the unmodified row routine at 0x200010C8 while retaining bootstrap register state. Pressing contacts (0,3), (3,12) and (7,15) updates raw scan words to 0x00000008, 0x10000000, 0 and 0x80000000 over three selected passes; three release passes restore zero. The routine publishes one changed 32-bit pair of rows per pass through its existing dispatch table. The probe confirms instruction bytes remain unchanged. Its explicit routine selection is a component test, not an alternate production boot path or evidence of working USB key input.

A further private startup experiment attaches the contact model and compatible lighting targets at all four probed addresses (Flexcomm4 0x50/0x5F/0x53 and Flexcomm2 0x5C). At 543 ms it still reports 43 EZH instructions and the same HOLD, with no CPU faults or unsupported accesses. This does not establish that all four targets are physically present; they remain an explicit experimental topology, not the default board.

After adding the shared GPIO/EZH mux, a private component probe calls the original CPU pin-setup routine at 0x2000B57C and row-read routine at 0x2000B608. Holding contact (3,1) yields raw row 3 value 0xFFFD, row 2 remains 0xFFFF, and releasing the contact restores row 3 to 0xFFFF. The complete application image remains unchanged in RAM. The probe uses an explicit subroutine call and return loop outside the application image; production startup remains unchanged and still reaches the existing EZH HOLD. Synthetic integration covers GPIO aliases/masks, preservation of unrelated pins, high-impedance rows, and switching row ownership between CPU GPIO and EZH through IOCON.

The in-process host also supports interrupt IN packet reads, with per-endpoint polling cadence, bounded virtual-time deadlines, short packets, zero-length packets and STALL reporting. Reset and disconnect discard the polling schedule. Tests prime native controller buffers between polling slots to check that timeout does not introduce an early poll. No HID payload is generated by the host.

A private component experiment connects the EZH common interrupt to NVIC30 and explicitly selects the original row routine after observing the normal startup HOLD. Pressing electrical contact (3,1) then produces endpoint 0x81 data `0000040000000000` through the original Arm key-processing and USB code. Releasing the contact clears the raw matrix and produces the matching all-zero release packet after 47 ms of virtual time; a shorter 20 ms observation had timed out. This validates a press/release matrix-to-USB path under experimental entry/routing choices, not normal boot or complete key handling. Separately, the firmware accepts HID SET_IDLE/GET_IDLE on all five interfaces, but no idle IN packet is observed during bounded polling; accepting those requests does not imply automatic report scheduling.

A further ordinary-host initialization probe reads all five report descriptors and performs SET_IDLE, SET_PROTOCOL(report) and GET_PROTOCOL for every interface. All requests complete and protocol readback is 1. At 193,890 µs EZH still reports 43 instructions at 0x200010AC and the NOP at 0x200010A0 remains unchanged, with no CPU faults or unsupported accesses. This does not support a HID initialization request as the missing scanner-start transition. The private-image USB integration test additionally exercises boot/report protocol and nonzero/zero idle-rate transitions through firmware.

## Separate GPIO input evidence

The CPU's independent button sampler reads a two-entry table at 0x20013B94, containing GPIO1 pins 28 and 26; its event IDs are 0xC8 and 0xF9. The two-phase sampler at 0x200130B8 reads GPIO1 pins 2 and 3, and its consumer at 0x20010AB4 recognizes phase transitions and dispatches event IDs 0xCC/0xCE. This supports a rotary input inference without establishing rotation direction or a physical connector pinout. These are separate from the 8×16 scan contacts. GPIO1 pin 6 is also read by a separately debounced input; its physical purpose is not established here.

An earlier private probe polled endpoint 0x85 for independent-button reports and saw none. That endpoint was the wrong observation point for the captured media bindings: subsequent normal-boot tests on endpoint 0x82 receive mute press/release from GPIO1 pin 28. The firmware readiness flag at 0x2002522E is 1 after ordinary USB enumeration, and its timer-derived counter advances once per modeled millisecond. EZH HOLD therefore does not prevent this independent Arm media path from running. No forced readiness flag or synthetic HID response is used.

## USB/IP host integration

`razer_emu.usbip` uses Python's standard asyncio streams and the existing firmware packet host. Renode 1.17.0's USB/IP server was inspected first: its unlink command is ignored and its reply path does not preserve STALL status. A small separate transport avoids changing or vendoring that implementation. All core access stays on the owning thread. Firmware supplies descriptors and class replies; no HID reports or Razer commands are implemented in the adapter.

The bridge resets and assigns server-side address 1 on import. This is required because Linux VHCI completes SET_ADDRESS locally without transmitting it to the exported device. The client subsequently sends SET_CONFIGURATION to the real firmware USB stack. Endpoint sizes and high-speed polling periods are parsed from the firmware configuration. An interrupt NAK keeps the URB pending; cancellation removes it and returns RET_UNLINK without a later RET_SUBMIT. Unsupported endpoint transfers return EPIPE; malformed/isochronous requests close the transport. Control transfers remain synchronous and bounded, so cancellation cannot interrupt an in-progress control request.

An isolated QEMU/KVM Linux 7.2.11 guest using the upstream USB/IP client attached over user-mode networking to the loopback-bound server. It read VID/PID 1532:02A5 and product string Razer BlackWidow V4 75%, bound all five HID interfaces and created hidraw0–4 plus keyboard/mouse input devices. A guest hidraw HIDIOCSFEATURE/HIDIOCGFEATURE exchange then returned status 02, command 00/87 and version 1.1.1. Host kernel modules and the physical keyboard were not involved. Windows/Synapse are not verified. This transport result does not establish scanner startup or working normal key input.

The OS-driven run with matrix contact (3,1) held ended at 423,980 virtual microseconds with EZH still at 0x200010AC after 43 instructions, holding. No CPU fault or unknown MMIO access was reported. The original NOP and inline pointer table at 0x200010A0 remained unchanged. Linux HID initialization and the Razer version request therefore do not resolve the scanner checkpoint.

## Media-wheel phase inputs

The original 1.1.1 function at 0x200130B8 reads encoded pin IDs 0x0201 and 0x0301 through the GPIO byte-alias helper at 0x20007D2C: GPIO1 pins 2 and 3. It stores the two levels at 0x20024CEC. The initialization routine at 0x20013164 seeds the decoder history; the consumer at 0x20010AB4 recognizes the phase transition patterns and dispatches internal keys CE/CC.

A private component probe attached the public encoder API before ordinary USB enumeration, then explicitly called the original initialization and consumer routines with interrupts masked and a diagnostic return loop outside the image. Starting high/high, A-leading-fall phases (10,00,01,11) produced direction flag 01; the reverse sequence (01,00,10,11) produced flag 02. A read-only CPU-address observer recorded two CE dispatches for the first electrical cycle and two CC dispatches for the reverse. This does not establish how electrical cycles relate to physical detents. These are component results, not an alternate production boot path. The complete application RAM image remained unchanged. The physical direction, contact timing and detents per revolution are unverified.

The core exposes contact levels only. Renode GPIO receiver inputs preserve them across MCU reset and prevent weak IOCON pulls from replacing an externally supplied level. The firmware decides decoding and actions; the encoder model emits no HID or Razer responses.

## Native flash execution and optional cold boot

The flash model now implements Renode's `IExecutableIO` interface, which routes instruction fetch through peripheral read methods. Its byte, word, doubleword, quadword and multi-byte reads retain the same 16-byte ECC validity checks; it is not replaced by direct mapped RAM. Flash load, erase and program operations invalidate translated instruction blocks using Renode's memory invalidation API. A synthetic test executes code from flash, erases/reprograms it, observes the new instructions without resetting the CPU, and verifies that core reset preserves the programmed code in bootloader mode. Another test checks erased-data and erased-instruction fetch faults. Renode currently reports an IO-backed instruction-fetch failure through its generic bus-fault path: exact architectural IBUSERR and instruction fault-address reporting are not modeled.

`Bootloader.load_dump()` validates capture integrity, requires all 32 KiB at address zero to be verified, and checks the stack and Thumb reset vector. With this optional image, the core starts at its reset vector with cleared SRAM; the original bootloader chooses/copies the application and sets its vectors. Flash images are loaded once when the board is created, so this mode preserves application programming across reset. The default application-handoff mode retains its existing image reload behavior. MCU internal ROM boot and electrical power-on behavior remain outside this path.

The private complete bootloader (SHA-256 a34935e307515302d8c082c3c85a792d7109699d0105dbebdbfdd11577b63acd), slot B and settings captures run through the real ECC-aware flash model without a diagnostic mapping. The CLI enumerates the original application USB device, runs to 144,770 virtual microseconds without a CPU fault or unknown MMIO, and still observes EZH holding at 0x200010AC after 43 instructions. The integration test checks a second boot following reset as well. This supersedes the earlier mapped-memory experiment as evidence of a supported cold-boot path; it does not resolve scanner startup.

The complete bootloader also clarifies its class 10/83 verify command: logical addresses 20000000–2001DFFF are translated to application flash (subtract 20000000, add 8000, then select the appropriate slot). The response copies from that flash address. This is not an arbitrary live-SRAM getter and does not provide a read-only USB route to the physical keyboard's executing EZH bytes. No additional physical requests were sent for this inspection.

Implementation reference: [Renode IExecutableIO](https://github.com/renode/renode-infrastructure/blob/8a748509bb4e8bae45d9cdfb5ab25e1bc4e37e4d/src/Emulator/Main/Peripherals/IExecutableIO.cs), [Renode mapped-memory invalidation](https://github.com/renode/renode-infrastructure/blob/8a748509bb4e8bae45d9cdfb5ab25e1bc4e37e4d/src/Emulator/Main/Peripherals/Memory/MappedMemory.cs).

## Normal media input pipeline

An uninstrumented application run with matrix, encoder and independent-button contacts attached confirms that ordinary USB enumeration enables the Arm media-input path. After a further 5 ms of virtual time, electrical phases (11,10,00,01,11) produce two volume-down actions, and the reverse cycle produces two volume-up actions. Endpoint 0x82 returns 22-byte report-ID-2 packets containing consumer usages 00EA/00E9, each followed by an all-released consumer report. Holding GPIO1 pin 28 low and releasing it for 40 ms each produces usage 00E2 (mute) and release. The complete application image remains unchanged and EZH still holds at 0x200010AC after 43 instructions. These are normal firmware-execution results, not the earlier explicit component-entry probes.

`Keyboard.attach_buttons()` uses Renode's existing inverted `Miscellaneous.Button` for the independent GPIO1 pins 28/26. Input indices follow the firmware table's internal keys C8/F9; physical positions and the F9 special action are not guessed. Native GPIO receiver state keeps contacts separate from weak IOCON pulls and preserves them across core reset. The encoder and button objects supply only electrical levels. Firmware performs debounce, decoding, binding lookup and report generation.

The CPU row-reading helper at 0x2000B608 is called by the separate check at 0x20008FA8. Its presence is not evidence of a working main-loop CPU fallback scanner. Normal matrix key reports remain unresolved; successful media reports must not be presented as successful matrix scanning.

The same normal media path was verified through USB/IP in an isolated QEMU Linux guest, starting with the complete captured bootloader. A guest evdev client opened the enumerated input devices and signaled readiness over a private loopback test channel; the library then drove only encoder phases and button index 0. Linux received KEY_VOLUMEDOWN (114), KEY_VOLUMEUP (115) and KEY_MUTE (113), each with values 1 (press) and 0 (release). The guest also completed the original Razer 00/87 version query. Mute auto-repeat events (value 2) were generated by Linux while the 40 ms virtual hold spanned a longer wall interval. USB/IP virtual time is not wall-clock synchronized. The private synchronization harness is not part of the production server or package. No physical keyboard input or host kernel USB/IP module was used.

## Register-substitution audit and native Razer query

A private diagnostic copy of the EZH model logs every `WriteDoubleWord` entry, while bus watchpoints independently cover all control-register addresses through both 4001D000 and 5001D000 aliases. Native cold boot, USB enumeration and a further 300 ms produce 319 writes in each trace: 316 to CTRL, two to ARM2EZH and one to BOOT. None use the secure alias; no write configures BREAK_ADDR, BREAK_VECT, EMER_VECT or EMER_SEL. At 344,930 virtual microseconds those registers remain zero, the application is unchanged and EZH still holds at 200010AC after 43 instructions. This rules out a missed modeled-alias write as the cause of absent breakpoint substitution for this run. The diagnostic logging is not shipped.
